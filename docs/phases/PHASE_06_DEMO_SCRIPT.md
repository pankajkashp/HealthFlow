# HealthFlow — Devpost Demo Script

A click-by-click sequence for a recording or a live judged demo. Walks through all 12 PRS §22 MVP
success criteria using two of the six synthetic benchmark patients.

---

## 0. Setup (once)

```bash
cp .env.example .env
# Optional but recommended: set ANTHROPIC_API_KEY in .env for real LLM tool-calling reasoning.
# Without it, LLM_PROVIDER defaults to "scripted" — the same deterministic tool sequence, still
# gated by the exact same safety/verification layer, just without a live model call.
docker compose -f docker/docker-compose.yml up --build
```

Wait for `db` to report healthy and `api` to log `Application startup complete`. The `api`
container automatically runs `alembic upgrade head` and seeds the 6 benchmark patients before
starting — nothing to run by hand.

Open **http://localhost:3000**.

## 1. The standard approval path (Sarah Jenkins)

1. On the dashboard, the patient picker defaults to **Sarah Jenkins — MRI LUMBAR SPINE (Standard
   approval)**. Click **Start case**.
2. You land on the case detail page in `INITIATED` state. Click **Run agent**.
3. Narrate while it runs (near-instant on `scripted`, a few seconds on a real LLM): the agent is
   calling `get_patient_record`, `get_insurance_plan`, `get_authorization_requirements`,
   `get_required_document` (twice), `validate_authorization_package`,
   `submit_authorization_request`, `get_authorization_status`, `verify_authorization_outcome` — the
   full tool-call trace renders below with each call's arguments and result.
4. The case reaches **COMPLETED** with a green banner: *"Independently verified and completed. The
   agent never declared this DONE itself — an authoritative external check confirmed the outcome."*
5. Point at the workflow timeline: seven state transitions, each with the deterministic reason that
   caused it — this is the domain state machine, not the LLM, deciding what "done" means.

**Criteria covered:** #1 (case created), #2 (agent understands the goal), #3 (controlled tool
retrieval), #4 (deterministic validation), #5 (request prepared), #6 (submitted to the simulated
system), #10 (independently verified), #11 (never claims completion without verification), #12
(fully observable — every step is visible).

## 2. The safety story: false-success interception (Olivia Chen)

This is the flagship scenario — the reason the project exists.

1. Back on the dashboard, select **Olivia Chen — MRI CERVICAL SPINE (False-success (DONE-principle
   test))**. Click **Start case**, then **Run agent**.
2. Narrate: the payer portal's submission endpoint returns an apparent success acknowledgment
   (`AUTH-ACK-CHEN-006`, status `RECEIVED`) — a naive agent would stop here and declare victory.
3. Point at the last two tool calls in the trace: `get_authorization_status` shows a determination,
   then `verify_authorization_outcome` — a **separate, independent access path** — reveals the
   authoritative backend actually holds `DENIED`, not the expected `APPROVED`.
4. The case is blocked from `COMPLETED` and instead reaches **ESCALATED**, with an amber banner:
   *"If the payer portal reported apparent success but independent verification didn't confirm it,
   the agent is blocked from declaring completion."*
5. Point at the final workflow transition's reason: *"Independent verification did not confirm
   expected outcome: Authoritative state mismatch: expected 'APPROVED', but authoritative external
   state is 'DENIED'."* — written by deterministic code, not generated by the LLM.

**Criteria covered:** #9 (escalation for an ambiguous/critical situation), #10 and #11 again, this
time under adversarial conditions — proving the DONE principle holds even when the external system
itself reports a false success.

Available from the same picker, each demonstrating a different deterministic guardrail:

  synthetic document store.
- **Elena Rostova** (conflicting information) — escalates on a detected data conflict.
- **David Kim** (payer denial) — reaches `DENIED` on a legitimate, independently confirmed denial

## 4. Wrap-up talking points

- The agent (Claude, via Strands) reasons about *what to do next*; it never controls *whether a
  state transition is legal* or *whether the case is done* — both are deterministic code
  (`packages/domain`, `packages/safety`, `services/agent/.../state_sync.py`), unchanged from Phase 5.
- Every one of the 9 tools the agent can call is the same tool AD-014 locked in Phase 4 — nothing
  new was added to give the LLM more access.
- The LLM provider is swappable (`LLM_PROVIDER=scripted|anthropic|bedrock`) purely for demo
  reliability; the locked architecture's target (Bedrock) works unchanged once AWS access exists.
